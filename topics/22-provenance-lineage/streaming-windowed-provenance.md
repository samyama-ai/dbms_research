# Streaming and Windowed Provenance

> **Topic:** Provenance & Lineage · **ID:** `22-provenance-lineage/streaming-windowed-provenance` · **Status:** open

## 1. Problem Statement
Continuous queries over data streams (with sliding/tumbling/session windows, aggregation, and joins) produce a never-ending output. Capturing lineage naively means retaining, for every emitted result, pointers to the contributing stream elements — but as the stream advances, the cumulative lineage **grows without bound**, even though only a bounded window of recent input is *live*. The problem: **maintain provenance for continuous/windowed queries using memory bounded by the window (and result) size, not by the total stream length, while still answering lineage queries about recent (in-window) outputs.**

Variants: **(decision)** can query $Q$ over window $W$ be answered with provenance in $O(|W|)$ working memory? **(optimization)** minimize memory subject to answering provenance for all outputs whose window has not yet expired. **(approximate)** sketch-based provenance for aggregates with $\epsilon$-error. **(retrospective vs. live)** support provenance only for *live* (non-expired) results, vs. a bounded *retention horizon* for forensic/audit replay.

## 2. Mathematical Foundations
Streaming computation is constrained to **sublinear (ideally $O(\text{polylog})$ or $O(|W|)$) space**; the relevant model is the **sliding-window streaming model** (Datar–Gionis–Indyk–Motwani, "Exponential Histograms"), which maintains aggregates over the last $N$ elements in $O(\tfrac{1}{\epsilon}\log^2 N)$ space with $(1\pm\epsilon)$ error. Provenance must ride the same budget. The provenance semiring $\mathbb{N}[X]$ still governs *which* elements witness a result, but **expiry** acts as a homomorphism that retracts annotations whose source elements have left the window — formally, lineage is maintained modulo the ideal generated by expired variables. For **aggregation provenance**, the semiring is $\mathbb{N}$-weighted, and bounded-memory exactness is impossible for, e.g., distinct-count lineage (set membership over the window), forcing sketches (Count-Min, $\ell_0$-samplers) that yield *approximate* witnesses. Memory lower bounds come from **communication complexity** (e.g. INDEX, DISJOINTNESS) reductions standard in streaming.

## 3. State of the Art (SOTA)
- **Theory:** Sliding-window sketch literature (Exponential Histograms; Braverman–Ostrovsky smooth histograms, FOCS 2007) bounds *aggregate* maintenance; provenance-specific bounds are sparse.
- **Systems:** **Ariadne** (Glavic, Sheykh Esmaili, Fischer, Tatbul; DEBS/EDBT 2013–14) is the canonical fine-grained provenance system for stream processing, capturing lineage for windowed operators with reduced overhead via lazy retention. **GeneaLog** (Palyvos-Giannas, Gulisano, Papatriantafilou; 2018) provides low-overhead backward provenance for streaming with bounded per-tuple metadata. Provenance in **Apache Flink/Storm/Spark Streaming** is mostly coarse (operator/lineage-graph level), not per-tuple-bounded. **Nexmark**-style benchmarks lack provenance.

## 4. Upper Bound
For windowed SPJ and monotone aggregation, **GeneaLog** maintains backward provenance with **$O(1)$ extra metadata per tuple** by exploiting the contiguity of window contents (delimiting in/out tuples), so total provenance memory is $O(|W| + |\text{live output}|)$ — bounded by the window, independent of stream length. For aggregate provenance under approximation, sliding-window sketches give $(1\pm\epsilon)$ witnesses in $O(\tfrac{1}{\epsilon}\log^2 N)$ space. Ariadne's lazy scheme reconstructs lineage from retained window state, trading recompute time for space. These are the systems-SOTA upper bounds.

## 5. Lower Bound
Exact provenance for general windowed aggregation requires $\Omega(|W|)$ space — a tuple may at any time be queried for its full witness set, and **communication-complexity** reductions (INDEX over the window) show no $o(|W|)$ exact scheme exists for distinct-element or set-valued lineage. For unbounded *retention* (answering provenance for arbitrarily old outputs), space is $\Omega(\text{stream length})$ — an unconditional impossibility, formalizing the "grows without bound" obstruction. Multi-pass / persistence requirements compound this. Hence exact, full-history streaming provenance in bounded memory is **provably impossible**, which is *why* the problem is open: the live frontier is what tractable approximations and retention policies can guarantee.

## 6. The Gap
For *live, in-window, structural* (SPJ) provenance, the gap is essentially **closed** by GeneaLog-style $O(|W|)$ schemes. The genuinely **open** part: (1) bounded-memory **approximate** provenance for set-valued/distinct aggregates with formal error guarantees (the sketch-provenance theory is underdeveloped); (2) provenance under **out-of-order / late / retracting** streams (watermarks, exactly-once) where expiry is non-monotone; (3) a principled **retention-horizon** model trading audit completeness against bounded memory. No dichotomy exists for which windowed queries admit $O(|W|)$ exact provenance.

## 7. Current Research (as of June 2026)
- Extending **GeneaLog / Ariadne** to out-of-order and exactly-once semantics aligned with Flink watermarks (Gulisano, Glavic groups) *(frontier — verify)*.
- **Sketch-based approximate provenance** for streaming aggregates with $(\epsilon,\delta)$ guarantees; $\ell_0$-sampler-backed witness recovery *(frontier — verify)*.
- Provenance for **streaming ML / feature pipelines** where windows feed online models; intersects dataflow-pipeline provenance.

## 8. Future Work
A formal sliding-window provenance model with tight space lower/upper bounds per operator class. Approximate set-valued lineage with guarantees. Non-monotone expiry under retractions/late data. Retention-horizon policies with audit-coverage SLAs. Benchmarks (a "provenance Nexmark").

## 10. Worked Example

Consider a count-based sliding window of size $N=4$ over a stream of sensor readings and the continuous query $Q$: "emit the max of the current window." Stream prefix (newest on right):

$$\ldots,\; r_5{=}3,\; r_6{=}9,\; r_7{=}2,\; r_8{=}5 \quad(\text{window} = \{r_5,r_6,r_7,r_8\}).$$

The output is $\max = 9$, with **backward provenance** $\{r_6\}$ — the single witness. A naive scheme storing, for every emitted max ever, a pointer to its witness uses $\Theta(\text{stream length})$ memory. GeneaLog instead keeps $O(1)$ metadata per *live* tuple and reconstructs witnesses from the retained window, so memory is $O(|W|)=O(4)$ regardless of how long the stream runs.

Now advance one step: $r_9{=}1$ arrives, $r_5$ expires. Window $=\{r_6,r_7,r_8,r_9\}$, still $\max=9$, witness still $\{r_6\}$. When $r_6$ eventually expires, the witness must be recomputed — illustrating non-trivial expiry. Contrast distinct-count: an INDEX-style communication lower bound forces $\Omega(|W|)$ space for exact set-valued lineage, which is *why* approximate sketches are needed there.
