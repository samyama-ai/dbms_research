# Iteration 2026-09 — verify the references, don't regenerate the problems

## What this iteration did, and why it is not what the runbook says

The refresh runbook's Phase 1 is "re-identify the problem space" — regenerate a fresh
candidate set of 1000+ problems and diff it against the existing catalogue. That was not run.

Regeneration draws candidates from the same model that wrote the catalogue, so it repeats the
construction bias without touching the actual weakness. The measured weakness was this:

```
1,053 problems / 35 topics
provenance    synthesized: 1053    verified: 0
last_reviewed 2026-06: 1041   2026-07: 6   2026-09: 6
6,132 references, none ever resolved against a bibliographic source
```

Every reference in the catalogue was asserted, never checked. So this iteration checked them.

Existence, independently, against the DBLP bulk dump of 2026-09-07 (8,719,122 records):
**5,401 of 6,132 references matched by exact title**, and of the 538 distinct titles left,
518 matched fuzzily. **17 distinct titles have no plausible DBLP record** — every one checked
by hand is a real source DBLP does not index (Kx and Vitess documentation, an AWS ClockBound
repository, a 1934 JRSS paper, a Microsoft tech report), plus one the catalogue itself already
marks `*(unverified)*`.

**No fabricated citation was found.**

Per file: **1,019 of 1,053 have every reference verified**; 34 files carry 35 references no
source could confirm, recorded as `refs_unverified` in their frontmatter.

## Frontmatter

New field on all 1,053 files:

```yaml
refs_checked: 2026-09        # every section-9 reference resolved against a bibliographic source
refs_unverified: <N>         # omitted when 0
```

`provenance` stays `synthesized` on all 1,053. The references were machine-checked; the prose
was not, and a field that claimed otherwise would be the same defect this iteration exists to
find. `last_reviewed` was bumped only on the 22 files whose content actually changed.

## Not done in this iteration

- **Phase 1 re-identification** — deliberately skipped, see above.
- **Section 5/6 SOTA and bounds prose** — unverified. This iteration verified that the
  references exist and are the papers claimed, not that the claims made about them hold.
- **The `*(frontier — verify)*` flag** — still boilerplate on ~1,043 files. Clearing it
  honestly requires reading the claim, not the citation.

## Next iteration — target `2027-01`

Recorded here so the plan is public and arguable, not inherited.

**The recommendation is not to regenerate the problem set.** Skipping regeneration was right
for `2026-09` because the catalogue's weakest property was that nothing in it had been checked
against a source. That is no longer true.

**The gap that now dominates is the prose.** This iteration established that the citations are
the papers claimed. It established nothing about whether the section 5 SOTA summaries and the
section 4/6 bounds are *correct*. The `*(frontier — verify)*` flag on ~1,043 of 1,053 files is
the same problem wearing a label: applied that broadly it carries no information and cannot be
acted on. Clearing it honestly means reading each claim against its sources, which is a
substantially larger effort than this iteration — closer to the original catalogue build.

**Cheaper work that does not depend on that decision:**

- Re-run this iteration's reference verification. It is a scripted pipeline now
  (`tools/README.md`), it costs almost nothing, and it catches drift — a DOI that changes what
  it points at, or references added since.
- The 34 files carrying `refs_unverified` (35 references) are mostly vendor documentation and
  pre-CS-era papers. Decide whether to cite those differently rather than leave them flagged.
- Fix the extractor pollution behind the two residual bad person nodes in the derived graph.

**Regeneration is a question to re-answer, not a rule.** The argument against it is specific —
candidates come from the same model that wrote the catalogue, so it repeats the construction
bias. If the field visibly moves (a new subfield, a flagship problem closed), regeneration
becomes the right lane again.

## Tooling

`tools/README.md` documents the pipeline and the seven false-result classes that had to be
eliminated before any number here could be trusted. An exact-title check alone called 905
references missing; 884 of those were artifacts of the checker, not the catalogue.
